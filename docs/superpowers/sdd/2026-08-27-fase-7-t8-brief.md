## Passos

1. Implementar `pullChanges({ lastPulledAt, schemaVersion })` chamando
   `GET /sync/pull` e mapeando a resposta pro formato exato que `synchronize()`
   espera.
2. Implementar `pushChanges({ changes, lastPulledAt })` chamando `POST /sync/push`;
   tratar `409 SYNC_CONFLICT` deixando o `synchronize()` fazer o retry automático

3. Confirmar que `synchronize()` é chamado dentro de `syncGuard.runWithLock` — mesma
   proteção contra chamadas concorrentes que existe hoje, só trocando o corpo
   executado.
4. Testes: mock do `pullChanges`/`pushChanges`, provar que 2 chamadas concorrentes
   de sync não corrompem estado (mesmo teste que já existe pra `syncGuard.ts` hoje,
   adaptado).
5. Teste de regressão do bug original (motivo desta fase inteira): simular pedido
   com item novo local + `isOpen` alterado remotamente entre `lastPulledAt` e o
   push — provar que o pull (que roda antes do push no `synchronize()`) já resolve
   o valor de `isOpen` antes do push acontecer.
6. Rodar suíte completa + `tsc --noEmit`.

## Contrato exato da api (Task 3, já implementada e aprovada em `api-tozzo.uk`,
## `modules/sync/sync.controller.ts` + `modules/sync/sync.routes.ts`) — NÃO precisa
## ler o repo da api, o contrato completo está aqui:

### `GET /sync/pull?lastPulledAt=<epoch ms ou vazio>&schemaVersion=<n>`

Auth: `Authorization: Bearer <token>` (mesmo token JWT normal, não é token curto de
SSE). Resposta 200:

```json
{
  "changes": {
    "products": { "created": [...], "updated": [...], "deleted": ["id1", "id2"] },
    "product_types": { "created": [...], "updated": [...], "deleted": [...] },
    "orders": { "created": [...], "updated": [...], "deleted": [...] },
    "order_items": { "created": [...], "updated": [...], "deleted": [...] },
    "sales": { "created": [...], "updated": [...], "deleted": [] },
    "sale_items": { "created": [...], "updated": [...], "deleted": [...] }
  },
  "timestamp": 1234567890123
}
```

`deleted` é sempre array de string (id). Chaves de `changes` usam snake_case (nomes
de tabela Watermelon), 6 coleções fixas: `products`, `product_types`, `orders`,
`order_items`, `sales`, `sale_items`. `timestamp` é epoch ms (usar como próximo
`lastPulledAt`). Erros: 400 `INVALID_SYNC_PULL` (params inválidos, ex.
`schemaVersion` ausente), 500 `SYNC_PULL_FAILED`.

### `POST /sync/push`

Auth: mesmo Bearer token. Body:

```json
{ "changes": { /* mesmo formato created/updated/deleted por tabela, sem timestamp */ }, "lastPulledAt": 1234567890123 }
```

Resposta 200:

```json
{ "ignored": [ { "type": "product|order|sale", "entityId": "id ou null", "reason": "string" } ], "ignored_order_deletes": [ /* mesma forma, motivo específico de delete de pedido aberto */ ] }
```

`ignored`/`ignored_order_deletes` são extensões não-padrão (fora do protocolo
Watermelon puro) — itens inválidos são pulados individualmente e reportados aqui,
NUNCA travam o push inteiro (padrão já usado no resto do projeto, ver
`sincronizacao.controller.ts` legado — "erros de sync não devem derrubar a
transação inteira"). O worker de `pushChanges` do mobile deve logar/reportar esses
itens ignorados de alguma forma visível (não silenciar), mas não precisa tratar
como erro fatal.

Erro de conflito: **409**, corpo `{ "error": "SYNC_CONFLICT", "message": "...",
"details": [ { "table": "orders|sales|products|product_types", "id": "..." } ] }`
— acontece quando o servidor tem uma versão mais nova do registro do que a que o
client está tentando sobrescrever (optimistic concurrency check). O `synchronize()`
nativo do Watermelon já sabe fazer pull+retry automático quando o push falha por
conflito — não escrever lógica de retry manual, só garantir que o erro 409 é
propagado de um jeito que o `synchronize()` reconheça como motivo de retry (ver
documentação/tipos do `@nozbe/watermelondb/sync` já instalado no projeto).

Erros não-conflito: 400 `INVALID_SYNC_PUSH` (payload inválido), 500
`SYNC_PUSH_FAILED`.

## Padrão obrigatório herdado das Tasks 5-7 (não está listado nos critérios acima,
## mas é requisito de revisão em toda task que toca dado local)

Toda query/mutação de dado local no Watermelon precisa ser escopada por
`establishmentId` do estabelecimento autenticado. O `pullChanges`/`pushChanges`
novos herdam isso automaticamente da api (que já escopa por `establishmentId` do
token) — mas confirme que nenhuma escrita local do sync novo bypassa esse
isolamento (ex: aplicar mudanças puxadas de um pull sem checar que pertencem ao
estabelecimento ativo, embora a api já devesse garantir isso — defesa em
profundidade, não confiar cegamente).

## Contexto do bug original que motivou a fase inteira (não repetir)

Ver `plano.md`, seção "Fase 7", "Contexto — achado durante QA manual da Fase 6": o
sync caseiro antigo empurrava a linha inteira em vez de campo alterado, causando
"o pedido volta pra aberto" quando editado na web e no app quase ao mesmo tempo. O
motor Watermelon resolve isso puxando (pull) o estado mais recente do servidor
ANTES de empurrar (push) as mudanças locais — o teste do Passo 5 acima existe
especificamente pra provar que essa ordem resolve o bug de verdade.
