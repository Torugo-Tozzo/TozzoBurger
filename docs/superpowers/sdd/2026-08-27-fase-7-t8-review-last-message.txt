Isso prova a ordem e o estado aplicado antes do push.

2. **❌ Isolamento não é robusto em todos os caminhos.** A defesa para `products`/`orders`/`sales` e para referências de `order_items`/`sale_items` existe (`database/watermelon/sync.ts:L281-L332`). A exceção de `product_types` sem `establishment_id` é aceitável sob o contrato atual: a tabela é global no schema (`database/watermelon/schema.ts:L23-L30`) e o endpoint é escopado pelo Bearer token. Porém, o guard falha aberto sem `establishmentId`, não verifica colisão de IDs de child rows e não valida relações `sales.order_id`/`orders.seller_id`/`sales.seller_id`; isso impede considerar o isolamento completo aprovado.

O retry permanece dentro da única execução de `runWithLock`, porque o loop está dentro de `synchronizeWithServer` e os consumidores adquirem o lock somente fora dela (`context/AuthContext.tsx:L198`, `context/AutoSyncContext.tsx:L52`). O contrato reserva 409 para conflito; há uma ressalva menor no predicado permissivo, registrada abaixo.

## Achados

- [Important] **A validação de tenant falha aberto quando `establishmentId` está ausente.** `ensureTenantScope` retorna sem verificar nada em `database/watermelon/sync.ts:L281-L283`; `AutoSyncContext` só exige token (`L42-L55`) e pode iniciar o sync no efeito de token antes de o perfil ter carregado (`L123-L131`), enquanto `AuthContext` define o token antes de concluir `getMe` (`L42-L46`). Nesse intervalo, o pull pode ser aplicado e mudanças locais podem ser enviadas sem a defesa local de tenant. O token é a proteção remota prevista pelo contrato, mas isso viola a exigência explícita de defesa em profundidade e não é fail-closed.

- [Important] **O cursor nativo de sync não é separado nem resetado na troca de estabelecimento.** O Watermelon guarda um único `__watermelon_last_pulled_at` no adapter (`node_modules/@nozbe/watermelondb/sync/impl/index.js:L23-L46`). Ao mudar de estabelecimento, `AuthContext` chama `resetWatermelonLocalData` (`context/AuthContext.tsx:L153-L176`), mas essa função só apaga `products`, `product_types` e `printers` e não limpa o estado do sync nem os dados de `orders`/`sales` (`database/watermelon/database.ts:L32-L50`). Assim, uma sessão B pode enviar o timestamp da sessão A a `/sync/pull`; registros de B mais antigos que esse timestamp não serão retornados, deixando a base local de B incompleta. Mudanças A pendentes que permaneceram em `orders`/`sales` também podem bloquear o sync B pela validação de tenant.

- [Important] **A defesa de referências cruzadas não cobre toda a graph local nem colisões de child IDs.** `ensureChildReferencesBelongToEstablishment` valida o parent/product referenciado no payload (`database/watermelon/sync.ts:L198-L240,L242-L279`), mas não consulta uma `order_items`/`sale_items` existente com o mesmo ID para confirmar que ela já pertence ao mesmo tenant. O Watermelon atualiza um registro local quando o servidor envia um `created` com ID existente (`node_modules/@nozbe/watermelondb/sync/impl/applyRemote.js:L246-L270`), portanto uma colisão pode reescrever uma child row ligada a outro estabelecimento. Também não há verificação para `sales.order_id`, `orders.seller_id` ou `sales.seller_id`, embora sejam relações do schema/modelos (`database/watermelon/schema.ts:L39-L40,L63-L65`, `database/watermelon/models/Order.ts:L21-L23`, `database/watermelon/models/Sale.ts:L25-L28`). Isso é uma lacuna real na defesa em profundidade, mesmo com a API corretamente escopada.

- [Important] **Itens `ignored` pelo servidor são marcados como sincronizados pelo Watermelon sem terem sido aceitos.** `pushChanges` apenas loga `ignored`/`ignored_order_deletes` e resolve sem retornar `experimentalRejectedIds` (`database/watermelon/sync.ts:L351-L361,L404-L412`). A implementação nativa então usa o `localChanges` original e chama `markLocalChangesAsSynced`; sem IDs rejeitados, ela marca `created`/`updated` e destrói deletes (`node_modules/@nozbe/watermelondb/sync/impl/markAsSynced.js:L52-L63`). Como o contrato prevê itens ignorados individualmente, um produto/pedido/venda ignorado — especialmente um delete de pedido aberto — pode desaparecer da fila local e ficar divergente do servidor. O `console.warn` cumpre o requisito de visibilidade, mas não resolve a perda do estado de sincronização.

- [Minor] **O predicado de conflito é mais amplo que `409 + SYNC_CONFLICT`.** `isSyncConflictError` aceita qualquer erro com `status === 409` e também aceita o marcador `SYNC_CONFLICT` sem exigir status 409 (`database/watermelon/sync.ts:L365-L373`). O teste cobre rede, mas não um 409 não-conflitante (`database/__tests__/watermelonSyncRetry.test.ts:L94-L103`). O contrato atual reserva 409 para conflito, então isto não muda o comportamento de uma API conforme o brief; ainda assim, se outro 409 surgir, serão feitos até três ciclos desnecessários.
