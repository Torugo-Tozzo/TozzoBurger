   chamada de criação).
5. Rodar suíte focada + `tsc --noEmit`.

## Contrato exato da api (Task 2, já implementada e aprovada — `api-tozzo.uk`,
## `modules/establishments/` + `modules/product-types/`) — NÃO precisa ler o repo
## da api, o contrato completo está aqui:

### Enum de categoria (fixo, 6 valores, igual nos dois lados)

```
HAMBURGUERIA | PIZZARIA | SORVETERIA | CAFETERIA | LANCHONETE | OUTRO
```

### `GET /estabelecimentos`

Auth: Bearer token normal, qualquer role autenticado. Retorna o estabelecimento do
usuário autenticado, incluindo o campo `category` (uma das 6 strings acima, ou
`null` se ainda não configurado). Sem parâmetro de rota — sempre o estabelecimento
do token.

### `PATCH /establishments/:id`

Auth: Bearer token. **RBAC: só `OWNER` ou `MANAGER`** (403 pra qualquer outra
role). `:id` tem que ser o `establishmentId` do próprio usuário autenticado (senão
404). Body: `{ "category": "HAMBURGUERIA" }` (uma das 6 strings, case-insensitive
no servidor mas prefira enviar maiúsculo). 400 se `category` ausente ou inválida.
200 com o estabelecimento atualizado em caso de sucesso.

### `POST /tipos`

Auth: Bearer token. **RBAC: só `OWNER`** (403 pra `MANAGER`/`FUNCIONARIO`/`CLIENTE`
— mais restrito que o PATCH acima, atenção a essa diferença). Body:
`{ "description": "Lanches", "color": "#9E9E9E" }` (aceita também os aliases
`descricao`/`cor`, mas use os nomes em inglês). 201 com o tipo criado.

### ⚠️ Decisão obrigatória por causa do RBAC diferente entre os dois endpoints

`PATCH /establishments/:id` aceita `OWNER` ou `MANAGER`, mas `POST /tipos` só
aceita `OWNER`. Isso significa que, se um `MANAGER` for o primeiro a logar num
estabelecimento novo, ele consegue confirmar a categoria mas o passo de criar os
tipos de produto sugeridos vai falhar com 403 pra cada chamada. **Ruling do
controller**: restrinja o disparo do onboarding completo (tela + fluxo de
confirmação) só pra usuários com role `OWNER` — leia o role do usuário autenticado
(já disponível no `AuthContext`/`useAuth()`). Pra `MANAGER`/`FUNCIONARIO` com
`category === null`, NÃO mostre o onboarding (não tente e falhe parcialmente) —
documente essa decisão no relatório da task. Login como `OWNER` eventualmente vai
completar o onboarding pendente.

### Depois de confirmar (consideração offline-first)

Depois que `PATCH`/`POST` retornarem sucesso, os `ProductType` criados na api
precisam aparecer na lista local (Watermelon) do app. A forma mais simples e
consistente com o resto do projeto é disparar um ciclo de sync
(`runWithLock(() => synchronizeWithServer(token, establishmentId))`, de
`database/watermelon/sync.ts`, Task 8 já implementada e aprovada) logo depois de
criar os tipos — o próximo `pull` vai trazer os `product_types` recém-criados. Não
precisa upsert manual local dos tipos criados, e não precisa esperar o auto-sync
periódico — disparar explicitamente no fim do fluxo de confirmação é aceitável e
mais responsivo pra UX de onboarding.
