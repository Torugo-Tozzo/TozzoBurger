# Fase 6 — Plano de implementação de i18n e rename para inglês

> Pré-requisito: aprovação explícita do usuário para este spec e para o plano.

> rodada de brainstorm.

Spec: C:/RN/TozzoBurger/docs/superpowers/specs/2026-08-24-fase-6-i18n-design.md

## Objetivo

Migrar API, dashboard e app mobile para domínio/schema interno em inglês,
preservar o contrato HTTP legado na borda, manter o sync offline compatível e
entregar UI completa em en, pt-BR, es, fr, zh, hi e ar, com RTL real para ar.

A ordem obrigatória é:

1. migration e schema Prisma/Postgres;
2. nomenclatura interna e adapters de contrato nos três repositórios;
3. i18n, formatação e RTL nas duas interfaces;
4. validação integrada e QA nativo.

## Protocolo de execução

- Só começar depois da aprovação do usuário; a aprovação não autoriza
  automaticamente migration no banco real.
- Criar uma branch de feature separada em cada repositório, sempre baseada em
  dev. main fica intocada.
- Cada task de implementação será entregue a um subagente dedicado. Toda
  criação de subagente, inclusive reviewer e revisão final, deve declarar
  explicitamente model: gpt-5.6-luna e reasoning_effort: max. Nunca herdar o
  modelo da sessão nem usar outro identificador.
- O worker implementa a task com TDD, roda os testes focados e registra
  evidências. Um reviewer separado revisa a task antes da próxima; findings
  Critical/Important precisam ser corrigidos pelo worker e reavaliados.
- Ao terminar todas as tasks, um subagente de revisão final examina a branch
  completa, o diff entre dev e a árvore de cada repo, o blast radius e os
  critérios deste spec. Só depois o controller prepara os PRs destinados a
  dev.
- Nenhum worker pode usar prisma db push, reset, clean destrutivo, drop de
  tabela ou banco real sem uma autorização nova e explícita. A migration é
  testada primeiro em Postgres efêmero.
- Não traduzir nem sobrescrever nomes, ingredientes, clientes ou outros dados
  de negócio persistidos. Renomear identificadores de código e valores de
  máquina é diferente de traduzir conteúdo.
- Os três package managers permanecem: Bun na API/front e npm/Expo no mobile.
  Não criar package-lock no front nem bun.lock no mobile.
- Ao iniciar a execução, preservar alterações preexistentes e parar se a
  branch não tiver um baseline claro. O audit-context/ já existente em algum
  repo não faz parte desta fase e não deve ser removido.

## Task 1 — Migration manual do schema Prisma

### Objetivo

Renomear o schema Postgres sem drop/recreate e sem perda de dados.

### Arquivos principais

- Modificar: prisma/schema.prisma
- Criar: prisma/migrations/<timestamp>_rename_schema_to_english/migration.sql
- Modificar: prisma/seed.ts, prisma/seedProdutosTrailer.ts e types usados pelo
  seed
- Criar/modificar: testes de migração e invariantes em tests/prisma/ ou
  equivalente

### Passos

1. Escrever o teste/fixture de migration RED em Postgres efêmero: aplicar as
   migrations existentes, inserir um estabelecimento, usuário de cada role,
   produtos, tipos, pedido aberto/fechado, venda, itens, impressora e device.
2. Alterar o schema.prisma para os modelos, campos, enum e relações ingleses,
   incluindo os mapas físicos finais definidos no spec.
3. Escrever SQL explícito com ALTER TYPE, ALTER TABLE RENAME TO, ALTER TABLE
   RENAME COLUMN, rename de índices/constraints e UPDATE somente dos valores
   de role/status definidos.
4. Conferir que não existe DROP, TRUNCATE, DELETE de negócio, tabela paralela
   ou mudança de FK. Não alterar a política de soft delete nem ON DELETE.
5. Fazer o teste aplicar a migration e provar:
   - mesma quantidade de linhas;
   - mesmos IDs e valores de produto/cliente;
   - roles/status convertidos;
   - FKs de itens, pedido/venda e tenant funcionando;
   - índices/defaults presentes;
   - leitura e escrita pelo Prisma Client novo.
6. Atualizar seed para identificadores e logs ingleses, preservando os nomes e
   ingredientes portugueses dos produtos como dados de demonstração.
7. Rodar prisma generate, o teste de migration e typecheck.

### Critérios específicos de revisão

O reviewer deve procurar principalmente migration destrutiva, enum default
quebrado, constraint apontando para nome antigo, role antiga escapando do
UPDATE e qualquer alteração acidental em timestamps/soft delete.

## Task 3 — Sync crítico: adapter legado, push/pull e regressão

### Objetivo

Garantir que sincronizacao permaneça funcional durante e depois do rename.

### Arquivos e áreas

- Renomear modules/sincronizacao para modules/sync.
- Renomear tipos/schemas de sync para nomes ingleses.
- Criar adapter de wire legado para push/pull.
- Atualizar tests/sincronizacao para o novo caminho, ou seu equivalente inglês,
  mantendo fixtures do contrato legado.
- Atualizar app.ts e a lista de endpoints sem trocar a URL.

### Passos

1. Escrever testes RED de normalização para payloads com nomes PT, nomes EN e
   mistura controlada; rejeitar tipos inválidos sem aceitar ambiguidades.
2. Definir tipos internos ingleses para ProductSync, OrderSync, SaleSync,
   SyncItem e SyncBatch.
3. Mapear na borda produtos/products, pedidos/orders, vendas/sales,
   nome/name, preco/price, ingredientes/ingredients, criado_por/createdBy,
   deleted_at/deletedAt e demais campos atuais.
4. Preservar a semântica da transação: item inválido é incluído em ignorados e
   não aborta os demais itens.
5. Preservar resolução de seller dentro do mesmo establishment, mapeamento de
   IDs mobile/servidor, soft delete, updated timestamps e eventos SSE.
6. Serializar o pull no formato que o app antigo entende; permitir que o app
   novo normalize o mesmo formato para seu domínio inglês.
7. Testar, no mínimo:
   - push de produto novo e atualização;
   - pedido com produto válido e item inválido;
   - venda fechando pedido;
   - delete/soft delete;
   - criado_por pertencente e não pertencente ao tenant;
   - pull incremental e watermark;
   - ignorados sem rollback total;
   - isolamento entre estabelecimentos.
8. Executar a suíte completa da API e uma chamada de integração contra app.handle
   com fixture de payload legado.

### Critérios específicos de revisão

O reviewer deve tratar qualquer mudança de contrato sync como Critical até
provar compatibilidade. A revisão deve confirmar que não foi introduzido lock
booleano, catch silencioso, query SQL não parametrizada ou emissão duplicada de
evento.
