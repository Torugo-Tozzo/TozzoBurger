# Fase 6.9 — Impressão de pedido/venda (dashboard web) + larguras de papel no mobile

> Spec produzida via brainstorm conversacional em 2026-08-26. Caminho: arquitetural (2 repos, novo estado persistido, muda lógica de formatação existente no mobile).

## Objetivo

O dashboard web (`front/front-tozzo.uk`) ganha suporte a impressão de pedido/venda — hoje só o app mobile imprime (impressora térmica via Bluetooth/BLE). A coluna "Ações" das tabelas de pedidos e vendas (Fase 4, design system) já reserva o botão de imprimir (ícone `Printer` do `lucide-react`).

Escopo ampliado durante o brainstorm: além do botão em si, o formato do recibo (largura do papel) vira configurável — tanto no web (novo) quanto no mobile (hoje hardcoded em 48 colunas, correspondente ao padrão 80mm, apesar do código nunca ter documentado isso).

## Fora de escopo

- Impressão de **pedido** no mobile — hoje o mobile só imprime **venda**; esta fase não adiciona impressão de pedido lá, só generaliza a largura da impressão de venda que já existe.
- Impressão térmica direta via Web Bluetooth no navegador — inviável de forma confiável entre browsers/impressoras (ver "Decisão técnica" abaixo).
- Qualquer endpoint novo na API — pedido/venda já chegam completos (com itens) nas tabelas do dashboard; a impressão renderiza a partir do dado já carregado em memória.
- Papel A4 como opção no mobile (BLE/ESC-POS é térmico, A4 não se aplica).

## Decisão técnica — por que não é "igual ao mobile"

O mobile manda bytes ESC/POS crus (`!0`, `E`, etc.) direto pra impressora via BLE (`hooks/formatarVendaImpressao.ts` + `useBLE.ts`), sem passar por driver nenhum. Um browser não consegue replicar isso de forma confiável: Web Bluetooth só existe em Chrome/Edge, e cada fabricante de impressora térmica tem um perfil BLE próprio — não há um protocolo universal como o ESC/POS-sobre-serial que o app usa.

Impressoras térmicas ligadas a um PC (USB ou rede) normalmente instalam como impressora comum do SO via driver do fabricante. A abordagem do web é: renderizar o recibo em HTML/CSS na largura certa e usar o diálogo de impressão nativo do navegador (`window.print()`), que já delega pro driver/OS escolher a impressora física. Mesmo **conteúdo** visual do recibo do mobile (cabeçalho, itens, total), mecanismo de impressão diferente.

## Larguras de papel suportadas

Seis opções (5 térmicas comuns + A4 só no web):

| Preset | Largura física | Uso típico | Colunas ESC/POS (mobile, Font A, aproximado) |
|---|---|---|---|
| `44mm` | 44mm | impressoras portáteis/bluetooth baratas | 24 |
| `58mm` | 58mm | POS/balcão pequeno, o mais comum junto do 80mm | 32 |
| `76mm` | 76mm | POS antigo / máquina de cartão | 42 |
| `80mm` | 80mm | **padrão atual hardcoded do mobile**, o mais comum no mercado | 48 |
| `110mm` | 110mm | impressora de cozinha / formato largo | 64 |
| `a4` | 210×297mm | só web, impressora comum a laser/jato de tinta | n/a (CSS, não ESC/POS) |

Os valores de colunas são aproximações-padrão de mercado pra fonte A a 203dpi — não há impressora física de 44/76/110mm pra calibrar contra nesta sessão. Ajuste fino futuro é mudança de 1 número na tabela, não redesenho.

## Armazenamento da preferência

Por **dispositivo/navegador**, não por estabelecimento — a impressora está fisicamente ligada a um computador específico do caixa, então cada PC configura a própria largura.

- Web: `localStorage`, chave `tozzo.printerWidth` (mesmo padrão já usado pra locale, `tozzo.locale`).
- Mobile: `AsyncStorage`, chave `@tozzoburger/printerWidth` (mesmo padrão do `LOCALE_PREFERENCE_KEY`).

## Arquitetura — Web (`front/front-tozzo.uk`)

**Abordagem de impressão**: container escondido renderizado na própria página (não abre aba nova). Um componente `ReceiptPrintRoot` fica montado fora do fluxo visual normal; ao clicar em "Imprimir", ele recebe os dados do pedido/venda, é preenchido, e `window.print()` é chamado. CSS `@media print` esconde todo o resto da página (`body > *:not(#receipt-print-root) { display: none }`) e mostra só o recibo. Evita bloqueio de pop-up e não precisa de rota nova.

**Componentes novos**:
- `src/lib/printPreferences.ts` — get/set do preset de largura no `localStorage`, mesmo formato de `src/i18n/locale.ts` (funções puras, fallback seguro).
- `src/components/receipt/ReceiptPrintView.tsx` — recibo em HTML puro, recebe `{ type: 'order' | 'sale', header, items, total, ... }` + preset de largura; usa flexbox (`justify-content: space-between`) pro alinhamento nome/preço em vez de contar caractere (limitação do ESC/POS que não existe em HTML/CSS).
- `src/components/receipt/receipt-print.css` (ou styled dentro do componente) — regras `@page { size: <width>mm auto; margin: 0 }` por preset, mais o bloco `@media print` que esconde o resto do app.
- `src/hooks/usePrintReceipt.ts` — hook que monta o `ReceiptPrintView` com os dados corretos e dispara `window.print()`.

**Pontos de integração**: o ícone `Printer` já reservado na coluna "Ações" de `PedidosTab.tsx` e `VendasTab.tsx` passa a chamar `usePrintReceipt` com o pedido/venda daquela linha (já em memória, sem fetch novo).

**Settings**: nova seção "Impressão" em `SettingsPage.tsx`, mesmo padrão visual da seção "Idioma" que acabou de ser feita (ícone — `Printer` do lucide — + `Select` do design system com as 6 opções). Persiste via `printPreferences.ts` ao trocar.

## Arquitetura — Mobile (`TozzoBurger`)

**Generalizar `formatarVendaParaImpressao`**: hoje o `48` está hardcoded na função (`hooks/formatarVendaImpressao.ts`). Passa a receber a largura selecionada (ou lê a preferência persistida) e usa a tabela de colunas acima em vez do número fixo.

**Componentes/mudanças**:
- `constants/printerWidths.ts` — a tabela largura→colunas (as 5 opções térmicas, sem A4) + tipo `PrinterWidthPreset`.
- `i18n/index.ts` (ou módulo próprio) — persistência da preferência via `AsyncStorage`, mesmo padrão de `setLocale`/`LOCALE_PREFERENCE_KEY` já existente ali.
- `hooks/formatarVendaImpressao.ts` — a função **não** ganha parâmetro novo: lê a largura persistida internamente, mesmo padrão de `i18n.language` que ela já importa hoje pro locale. A matemática de pontos (`numPontosLinha = 48 - ...`) passa a usar o número de colunas do preset lido em vez do `48` fixo.
- `app/(tabs)/configs.tsx` — a seção "Printer" (que já ganhou ícone/moldura nesta sessão) recebe mais um `Picker` — mesmo padrão do `Picker` de idioma — com as 5 larguras térmicas.
- `formatarVendaParaImpressao` passa a ser `async` (leitura de `AsyncStorage` é assíncrona) — os 2 pontos de chamada existentes (`app/(tabs)/historico.tsx`, `app/modais/contaHistoricoModal.tsx`) ganham `await` na chamada; ambos já estão dentro de funções `async` que fazem `await getPrinter()` ao lado, então é uma linha por call site, não mudança estrutural.
